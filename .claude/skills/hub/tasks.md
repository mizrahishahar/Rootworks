Teaches: how a task is written so it can be done and counted, how templates recur, and how the list is run: deadlines, priority, deferral, and the cut. The advice here is ruthless on purpose; a task list that is not ruthless is a wish list.

# Tasks

The Tasks table is the one list of work that outlives a session. Every session may create a task, every session writes them the same way, and this page is the way. The table's fields and the template mechanics are in the schema you are handed; read it, never remember it.

## A task

**Name.** Verb first, imperative: Check, Create, Write, Call, Review, Fix, Ship, Send, Launch. The object second, specific enough to know what is being touched without opening the row. Two to six words. No client in the name (Client carries it), no date (Due carries it), no colons, no quotes, no em dashes. English. A task born from a flag is named for the fix, not the symptom.

| Write this | Not this |
|---|---|
| Launch the bot campaign | Adelante: launch the "I built you a bot" campaign |
| Replace the dead sending domain | daveiodeploy.com has no replies |

**Steps.** Rich text; a step is a checkbox, `[ ] ` at the start of the line with nothing before it. A leading `- ` breaks the checkbox and the Progress count; never write `- [ ]`. One line, one action, starting with a verb. A step says where to go and what to flag, carries no reasoning, and states numbers bare ("Flag any inbox at 3% bounce or above"). A step you cannot tell you have finished is not a step; judgment words without a number are not steps. Three to eight; more than eight is two tasks. A Check task checks; its last step creates the tasks for what it found.

**Due.** The date it was meant to happen. It never moves on its own: a missed task sits overdue with its real date, which is the point.

**Status.** Todo, Doing, Done. Doing means a session is on it now, not "started once".

## Templates

A template is one task carrying its checklist; it never fans out into several rows. Recurrence and Day live on it. The spawner creates a task each morning for every template whose turn it is, and never a second one while one from that template is still open, so a missed occurrence is one overdue row, not a pile. Editing a template does not touch tasks already created.

## From a meeting

A meeting produces action points; action points become tasks linked through From Meeting. Read the meeting, propose the tasks in chat as a table (Task, Area, Client, Due, Steps), every name and step already in the shape above, wait for the yes, then write.

## Running the list

The Operator runs a company alone. The list exists so he never has to hold it in his head, and the advice below exists so the list stays a list of things that will happen.

**Deadlines.** A task gets a Due only if the date means something: a client waits on it, a campaign depends on it, a renewal lands. "Someday" gets no date. A date chosen to feel productive is a lie the list will repeat every morning.

**Priority, without a field.** There is no priority field by design. Priority is the order the list is worked, and the order comes from one question per task: what breaks, or who waits, if this slips a week. Money in and clients waiting come first; the machine's own hygiene comes last unless it is what blocks the first two. When asked to prioritize, answer with the list in order and one clause per task saying why it sits there.

**Overdue.** An overdue task is a decision not yet made. On every review, each overdue row gets one of three verbs: do it now, move Due to the real date it will happen, or delete it. Never a fourth. A row moved twice is deleted; it was never going to happen and the list is better without it.

**Deferral.** Deferring is honest when the new date is real and the reason is written in Notes in one line. It is dishonest when the date moves because the day ended. Say which one is happening.

**The cut.** When the open list passes what one person can carry in the time they have, the list is cut, not the person. Propose the cut: what stays, what moves, what dies, in a table, and the reason on each line. The Operator decides; the session never deletes on its own.

**Doing.** At most a few tasks in Doing at once. More than that is a Todo column wearing a different name.

**Checks.** A recurring Check is done when its findings are tasks. A Check that finds nothing three times in a row is a Check to question.

## How the list is shown

Whenever tasks are proposed or reviewed, one table, never inside a code fence, in the order they should be worked:

| Task | Area | Client | Due | Status | Why here |
|---|---|---|---|---|---|

Under it, the three lines when they apply: **Overdue:** each one with its verb. **Moved:** each one with its new date and reason. **Cut:** each one and why.

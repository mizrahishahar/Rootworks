# Launching

## How a machine starts

**Not every machine is launchable.** Every machine writes to Airtable, so nothing about the Hub tells you which ones you can start; the trigger nodes in the code do. Discovery is one command:

**[[LAUNCHERS]]** (`n8n/LAUNCHERS.md`) answers the three launch questions and nothing else:

- **What you can launch:** if a machine is in the table, you can start it. If it is not, you cannot; it runs on a schedule or is called by another machine.
- **How you launch it:** the Fire column is the exact request, method and full URL, ready to send.
- **What it needs:** the Fields column is the run's complete parameter list, from the machine's own launch form. Fill only these; they are also exactly what the pre-launch preview shows the Operator.

The file is generated by `node scripts/launchers.js`, never hand-edited; rerun it after every pull so it matches the code. When a payload detail goes beyond the field list, the machine's trigger node and the nodes right after it are the source.

Three ways a run begins:

- **A webhook fire.** POST the payload to the machine's webhook and it runs. This is how a session launches anything directly: build the payload, fire, watch the run row.
- **A Hub launch row.** Row-launched machines read their parameters from a row on the Automations table: Client, Table ID, and whatever else that machine reads (its source and the field descriptions in [[SCHEMA]] say which; fill only those). **Status mechanics: a row created with Status = Waiting is a held launch; clearing the Status fires the watching webhook and the run begins.** The row then lives its lifecycle: Running, then the verdict.
- **From Airtable itself.** The ClayRoots builders and their kin launch straight from their forms and record buttons; no session in the loop.

Client add-ons follow the `addon-{automation}-{clientslug}` webhook convention: a shared machine fires the add-on per client, 404-tolerant, so client-specific behavior attaches without forking the machine.

## Reruns

A past run's row carries its complete parameters, which makes any run repeatable: read the row, copy its variables into a new launch, verbatim for a pure rerun or with the named variable changed. The preview shows the delta against the original run.

## Attachments

**The API cannot write attachment fields**, and some machines take their input as a file (a CSV to ingest, a list to merge). [[LAUNCHERS]] marks these in its Attachment column, and they always use the held launch, in full:

1. Create the Automations row with **Status = Waiting** and every other parameter filled: Client, Table ID, the machine's own fields. Waiting means the watching webhook does not fire; the row just sits, complete except for the file.
2. The Operator opens the row and attaches the file by hand. That is the entire reason the hold exists.
3. The Operator clears the Status. The webhook fires, the row flips to Running, the machine reads the row, file included.

This is the one case where the Waiting hold is mandatory. Every other launch is guarded by the preview-and-approve and may fire directly.

## After the fire

The run row is the report: Running, then Succeeded / Succeeded with errors / Failed, with counts in and out, duration, and the per-run Description. Watch it there, not on the n8n canvas. And the row is still only a claim: done means **verified by cell values on the target table**, before and after counts, and what changed on a sample row.
